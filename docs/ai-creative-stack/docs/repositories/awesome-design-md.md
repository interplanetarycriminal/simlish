## Runtime, hardware and setup

- **Type** curated list.
- **Platforms** Unverified.
- **Runtime** None; plain Markdown files with YAML front matter, read by an AI agent or Google Stitch.
- **Execution** local.
- **Agent paths** Generic coding agent via project files, Google Stitch. Client claims describe documentation and remain untested here unless the smoke test says otherwise.
- **Configuration** None. Each file follows the Google Stitch DESIGN.md format with nine sections (theme, color roles, typography, components, layout, depth, do's and don'ts, responsive, agent prompt guide) and YAML front matter of tokens.
- **Credentials and services** None. Requesting a new DESIGN.md goes through the separate hosted service getdesign.md.

Review the source and pin the version before running the upstream-documented command. It was read in the pinned documentation; execution is recorded only under Smoke test.

```sh
1. Copy a site's DESIGN.md into your project root
2. Tell your AI agent to use it.
```

## Contracts and selection

| Boundary | Contract |
| --- | --- |
| Input | One of 84 brand DESIGN.md files in design-md/<brand>/ |
| Output | UI generated by your agent that follows the file's colors, type scale, component states and layout rules |
| Primary | Design-system extraction |
| Supporting | Creative direction, Discovery |

Skip when you need your own brand's design system or a license-clean identity; every file describes another company's brand. Consider [designlang](designlang.md). Complementary tools include [stitch-skills](stitch-skills.md), [react-bits](react-bits.md), [anthropic-frontend](anthropic-frontend.md).

No native integration with catalogue peers is asserted. Examples using another tool are proposed handoffs.

- Values come from public CSS at capture time and can drift as the live sites change.
- Maintainers no longer accept new DESIGN.md pull requests; new brands come through the getdesign.md request service.

## Craft notes

- 84 files across AI platforms, dev tools, fintech, retail, media, automotive and a retro-web series (Dell 1996, Nintendo 2001); each gives semantic color names with hex values, a full type hierarchy, component states, breakpoints and ready prompts.
- Files are framed as 'design-analysis' or 'Inspired' interpretations; the Stripe file deliberately spells the brand 'Stripi'.
- The README promises preview.html and preview-dark.html per site, but the pinned tree holds only DESIGN.md and a README per folder, and folder READMEs point to getdesign.md for previews.

## Examples

1. **Independent** Copy design-md/linear.app/DESIGN.md into a throwaway prototype and ask the agent for a settings page, to study how the file's spacing and type rules shape output.
2. **Combined** Proposed handoff: run designlang on your own site to produce a DESIGN.md, then compare its sections and token depth against an awesome-design-md reference file.

For both, save the inputs and output evidence with the selected version. Use a small authorized fixture first and review the actual render or inspection result before expanding scope.

## Security, privacy and licensing

- Markdown only, no executable code.
- Agents treat a DESIGN.md as authoritative instructions; review a file before placing it in a project.
- The files themselves send nothing anywhere. Requests through getdesign.md (including 'private requests') are a hosted service whose terms were not reviewed.

**Software license** MIT.

**Commercial use** MIT covers the repository's text, but the README says the files are extracted from public websites and that the maintainers do not claim ownership of any site's visual identity. MIT cannot grant rights the maintainers do not hold: brand names, logos, trade dress and proprietary fonts named in the files (for example SF Pro, Sohne) stay with their owners. Using a file to make a product that looks like a named brand risks trademark, trade-dress and font-license claims; commercial use of a brand's look is Not established and should be treated as reference only.
